## 一、线程基础

### 1. 进程和线程的区别？

- **进程**：资源分配的基本单位，拥有独立的内存空间（堆、方法区独立），进程间通信开销大（管道、Socket、共享内存等）。
- **线程**：CPU 调度的基本单位，同一进程内的线程共享堆和方法区，但每个线程有独立的**程序计数器、虚拟机栈、本地方法栈**。线程切换开销比进程小。
- 一句话：进程是"包工头分地盘"，线程是"工人干活"，工人共享地盘但各有各的工具箱。

### 2. 创建线程有哪几种方式？

1. 继承 `Thread`，重写 `run()`。
2. 实现 `Runnable`，作为 `Thread` 构造参数（推荐，避免单继承限制）。
3. 实现 `Callable`，配合 `FutureTask` / 线程池，**可返回结果、可抛异常**。
4. 通过**线程池** `ExecutorService` 提交任务（生产环境唯一推荐方式，阿里规约禁止手动 `new Thread`）。

> 本质上创建线程只有一种：`new Thread().start()`；其余都是对 `Runnable`/`Callable` 的封装。

### 3. `run()` 和 `start()` 的区别？

- `start()`：由 JVM 创建新线程并调用 `run()`，是真正的并发；一个线程只能 `start()` 一次，二次调用抛 `IllegalThreadStateException`。
- `run()`：普通方法调用，在**当前线程**同步执行，没有并发效果。

### 4. 线程有哪些状态？（Java 线程状态机）

`Thread.State` 枚举 6 种：

| 状态 | 说明 |
| --- | --- |
| `NEW` | 已创建未 `start` |
| `RUNNABLE` | 可运行（包含操作系统的 running 和 ready） |
| `BLOCKED` | 等待获取 `synchronized` 监视器锁 |
| `WAITING` | 无限等待，`Object.wait()` / `join()` / `LockSupport.park()` |
| `TIMED_WAITING` | 有超时的等待，`sleep(n)` / `wait(n)` / `join(n)` |
| `TERMINATED` | 执行结束 |

> 注意：Java 没有单独的 "running" 状态，`RUNNABLE` 同时代表就绪和运行中。

### 5. `sleep()` 和 `wait()` 的区别？

| 维度 | `sleep()` | `wait()` |
| --- | --- | --- |
| 所属类 | `Thread` 静态方法 | `Object` 方法 |
| 是否释放锁 | **不释放**锁 | **释放**对象锁 |
| 使用位置 | 任意位置 | 必须在 `synchronized` 块内 |
| 唤醒方式 | 时间到自动唤醒 | `notify()` / `notifyAll()` 或超时 |

### 6. `yield()`、`join()` 作用？

- `yield()`：提示调度器让出 CPU（不释放锁），但不保证生效，从运行态回到就绪态。
- `join()`：等待目标线程执行完毕（底层是 `wait`），常用于主线程等待子线程结果。

### 7. 如何优雅地停止一个线程？

- **不要用** `stop()`（已废弃，会立即释放所有锁导致状态不一致）。
- 推荐用**中断机制**：`thread.interrupt()` 设置中断标志，线程内部通过 `Thread.currentThread().isInterrupted()` 或捕获 `InterruptedException` 来协作式退出。
- 也可用 `volatile boolean flag` 做退出标志（但对阻塞中的线程无效，中断能唤醒阻塞）。

## 二、Java 内存模型（JMM）与 volatile

### 8. 什么是 JMM？

JMM（Java Memory Model）定义了多线程下**共享变量的可见性、有序性**规则。抽象为：每个线程有自己的**工作内存**（对应 CPU 缓存/寄存器），主内存保存共享变量。线程操作变量必须先从主内存拷贝到工作内存，改完再写回，由此产生**可见性问题**。

三大特性：**原子性、可见性、有序性**。

### 9. `volatile` 的作用和原理？

`volatile` 保证两点：

1. **可见性**：写 `volatile` 变量会立即刷回主内存，并使其他线程的缓存行失效（底层 CPU 的 MESI 缓存一致性协议 + `lock` 前缀指令）。
2. **有序性**：通过**内存屏障**禁止指令重排序（写前 StoreStore、写后 StoreLoad 等）。

**不保证原子性**：`i++` 是「读-改-写」三步，`volatile` 无法保证复合操作原子，需要用 `synchronized` 或原子类。

经典应用：双重检查锁定（DCL）单例中 `instance` 必须加 `volatile`，防止「分配内存-初始化-赋引用」重排序导致其他线程拿到未初始化对象。

### 10. 什么是 happens-before 原则？

用于判断两个操作是否有可见性/有序性保证的规则，无需关心底层重排序。常见规则：

- **程序顺序规则**：单线程内前面的操作 happens-before 后面。
- **锁规则**：`unlock` happens-before 后续对同一锁的 `lock`。
- **volatile 规则**：写 `volatile` happens-before 后续对它的读。
- **传递性**：A hb B，B hb C，则 A hb C。
- **线程启动规则**：`start()` happens-before 该线程内所有操作。
- **线程终止规则**：线程内操作 happens-before 其他线程 `join()` 成功返回。

## 三、synchronized 与锁

### 11. `synchronized` 的三种用法和锁对象？

- 修饰实例方法 → 锁 `this`。
- 修饰静态方法 → 锁 `类.class`（Class 对象）。
- 修饰代码块 → 锁括号里指定的对象。

### 12. `synchronized` 底层原理？

- 同步代码块：编译后生成 `monitorenter` / `monitorexit` 字节码，基于对象头的 **Monitor（管程/ObjectMonitor）** 实现。
- 同步方法：方法标志位 `ACC_SYNCHRONIZED`，隐式获取锁。
- 每个对象关联一个 Monitor，进入时 `_owner` 指向持有线程，`_count` 记录重入次数（**可重入锁**）。

### 13. 锁升级（偏向锁→轻量级锁→重量级锁）？

对象头 **Mark Word** 记录锁状态。JDK 6 后为优化 `synchronized` 引入锁升级：

1. **无锁 → 偏向锁**：只有一个线程访问时，Mark Word 记录线程 ID，下次直接进入，无 CAS 开销。
2. **偏向锁 → 轻量级锁**：出现第二个线程竞争，撤销偏向，用 CAS 自旋获取锁（适合锁竞争少、持有时间短）。
3. **轻量级锁 → 重量级锁**：自旋超过阈值/竞争激烈，膨胀为重量级锁，未获锁线程进入阻塞（涉及用户态到内核态切换，开销大）。

> 锁只能升级不能降级。JDK 15 起偏向锁被默认禁用/废弃（维护成本高）。

### 14. `synchronized` 和 `ReentrantLock` 的区别？

| 维度 | `synchronized` | `ReentrantLock` |
| --- | --- | --- |
| 层面 | JVM 关键字 | JDK 类（AQS 实现） |
| 加锁/释放 | 自动 | 手动 `lock()` / `unlock()`（需放 finally） |
| 可中断 | 不可 | `lockInterruptibly()` 可中断 |
| 公平锁 | 仅非公平 | 支持公平/非公平 |
| 超时获取 | 不支持 | `tryLock(timeout)` |
| 条件变量 | 单一 wait/notify | 多个 `Condition`，精准唤醒 |

## 四、AQS 与 CAS

### 15. 什么是 AQS？

AQS（`AbstractQueuedSynchronizer`）是 JUC 锁与同步器的**基础框架**。核心：

- 一个 `volatile int state` 表示同步状态（如锁重入次数、Semaphore 许可数）。
- 一个 **FIFO 双向队列（CLH 变体）** 存放等待线程。
- 通过模板方法（`tryAcquire`/`tryRelease` 等）由子类定义"如何获取/释放"，队列的排队、阻塞、唤醒由 AQS 统一管理。

`ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReentrantReadWriteLock` 都基于 AQS。

### 16. 什么是 CAS？有什么问题？

CAS（Compare And Swap）：`compareAndSet(expect, update)`，当内存值等于期望值时才更新，是一条 CPU 原子指令（`cmpxchg`），无锁并发的基础。

三大问题：

1. **ABA 问题**：值从 A→B→A，CAS 以为没变。解决：加版本号，`AtomicStampedReference`。
2. **自旋开销**：竞争激烈时长时间自旋空耗 CPU。可用 `LongAdder`（分段 + 最后汇总）缓解。
3. **只能保证一个变量原子**：多变量需封装到对象 + `AtomicReference`。

### 17. `AtomicLong` 和 `LongAdder` 的区别？

- `AtomicLong`：单个 value + CAS，高并发下大量线程 CAS 失败自旋，性能下降。
- `LongAdder`：**分段（Cell 数组）**，不同线程更新不同 Cell 减少竞争，`sum()` 时汇总。高并发写场景性能远优于 `AtomicLong`，但 `sum` 有瞬时误差、占内存更多。

## 五、线程池

### 18. 为什么要用线程池？

- 降低资源消耗：复用线程，避免频繁创建/销毁。
- 提高响应速度：任务到达即可执行。
- 便于管理：统一控制并发数、监控、调优。

### 19. `ThreadPoolExecutor` 的七大参数？

```java
new ThreadPoolExecutor(
    corePoolSize,     // 核心线程数
    maximumPoolSize,  // 最大线程数
    keepAliveTime,    // 非核心线程空闲存活时间
    unit,             // 时间单位
    workQueue,        // 任务队列（阻塞队列）
    threadFactory,    // 线程工厂（建议自定义命名，便于排查）
    handler           // 拒绝策略
);
```

### 20. 线程池的执行流程（任务提交后发生什么）？

1. 当前线程数 < `corePoolSize`：新建核心线程执行。
2. 已达核心数：任务入 `workQueue` 排队。
3. 队列满且线程数 < `maximumPoolSize`：新建非核心线程执行。
4. 队列满且线程数达 `max`：触发**拒绝策略**。

> 记忆口诀：**核心 → 队列 → 非核心 → 拒绝**。

### 21. 四种拒绝策略？

- `AbortPolicy`（默认）：抛 `RejectedExecutionException`。
- `CallerRunsPolicy`：由**提交任务的线程**自己执行（降速反压，不丢任务）。
- `DiscardPolicy`：直接丢弃新任务，不报错。
- `DiscardOldestPolicy`：丢弃队列中最老的任务，再尝试提交。

### 22. 为什么不推荐用 `Executors` 创建线程池？

阿里规约禁止，因为：

- `newFixedThreadPool` / `newSingleThreadExecutor`：用**无界队列** `LinkedBlockingQueue`，任务堆积可能 OOM。
- `newCachedThreadPool` / `newScheduledThreadPool`：`maximumPoolSize` 为 `Integer.MAX_VALUE`，可能创建海量线程导致 OOM。

应手动 `new ThreadPoolExecutor(...)`，明确参数与有界队列。

### 23. 线程池参数怎么设置（核心线程数）？

- **CPU 密集型**：`核心数 = CPU 核数 + 1`（减少上下文切换）。
- **IO 密集型**：`核心数 = CPU 核数 * 2`，或经验公式 `核数 * (1 + 平均等待时间/平均计算时间)`。
- 实际需结合压测和监控（队列长度、活跃线程、RT）动态调整，可用动态线程池（如美团 DynamicTp）。

## 六、Fork/Join 框架（重点）

### 24. 什么是 Fork/Join 框架？

Fork/Join 是 JDK 7 引入的**并行计算框架**，核心思想是**分治（Divide and Conquer）**：把一个大任务 `fork` 拆成若干小任务并行执行，再 `join` 把子结果合并。适合能递归拆分的**计算密集型**任务（大数组求和/排序、并行遍历等）。

核心类：

- `ForkJoinPool`：执行任务的线程池，`Java 8 parallelStream` 底层用的就是公共池 `ForkJoinPool.commonPool()`。
- `ForkJoinTask`：任务抽象，常用两个子类：
  - `RecursiveTask<V>`：**有返回值**，重写 `compute()`。
  - `RecursiveAction`：**无返回值**。

典型模板：

```java
class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;
    private final long[] arr; private final int lo, hi;

    protected Long compute() {
        if (hi - lo <= THRESHOLD) {          // 足够小，直接算
            long sum = 0;
            for (int i = lo; i < hi; i++) sum += arr[i];
            return sum;
        }
        int mid = (lo + hi) >>> 1;           // 拆分
        SumTask left  = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                          // 异步执行左半（放入当前线程队列）
        long rightRes = right.compute();      // 当前线程直接算右半（减少一次调度）
        long leftRes  = left.join();          // 等待并获取左半结果
        return leftRes + rightRes;
    }
}
// 使用：new ForkJoinPool().invoke(new SumTask(arr, 0, arr.length));
```

### 25. Fork/Join 的核心机制——工作窃取（Work-Stealing）是什么？

每个工作线程维护一个**双端队列（deque）**存放自己 `fork` 出的子任务：

- 线程处理**自己**的任务时，从队列**头部**取（LIFO，利于缓存局部性）。
- 当某线程**空闲**、自己队列空了，就去**其他忙碌线程队列的尾部**"偷"一个任务来执行（FIFO）。

好处：**负载均衡**，避免部分线程闲置；头尾两端操作减少竞争。这是 Fork/Join 高效的关键。

### 26. 使用 Fork/Join 的注意事项？

- **合理的拆分阈值 THRESHOLD**：太小 → 任务过多、调度开销压过收益；太大 → 并行度不足。需根据数据量和机器压测。
- **先 `fork` 后 `join`，且顺序要对**：推荐"左 fork、右 compute、再 join 左"，避免两个都 `fork` 后主线程空等，减少一次线程调度。
- **不要在 compute 里做阻塞 IO**：Fork/Join 面向计算密集型，阻塞会占死工作线程（IO 场景用普通线程池 / `CompletableFuture` / 虚拟线程）。
- **异常处理**：子任务异常在 `join()` 时以 `RuntimeException` 抛出，可用 `isCompletedAbnormally()` / `getException()` 检查。
- `parallelStream` 默认共用 `commonPool`，CPU 核数-1 的并行度，注意与其他并行任务互相影响，必要时自定义 `ForkJoinPool`。

### 27. Fork/Join 和普通线程池 `ThreadPoolExecutor` 的区别？

| 维度 | `ThreadPoolExecutor` | `ForkJoinPool` |
| --- | --- | --- |
| 任务模型 | 相互独立的任务 | 可递归拆分、有父子依赖的任务 |
| 队列 | 一个共享阻塞队列 | 每个线程一个 work-stealing deque |
| 适用场景 | 通用（含 IO 密集） | 分治型 CPU 密集计算 |
| 负载均衡 | 靠共享队列 | 工作窃取 |

## 七、CompletableFuture

### 28. `Future` 有什么局限？`CompletableFuture` 好在哪？

- `Future.get()` 是**阻塞**的，无法注册回调，多个 Future 组合困难，不能手动完成。
- `CompletableFuture`（JDK 8）支持：
  - 异步执行：`supplyAsync` / `runAsync`。
  - 链式回调（不阻塞）：`thenApply` / `thenAccept` / `thenRun`。
  - 组合：`thenCompose`（串行依赖）、`thenCombine`（两个并行结果合并）、`allOf` / `anyOf`。
  - 异常处理：`exceptionally` / `handle` / `whenComplete`。
- 默认使用 `ForkJoinPool.commonPool()`，生产建议传入**自定义线程池**避免公共池被占满。

## 八、并发容器

### 29. `HashMap`、`Hashtable`、`ConcurrentHashMap` 区别？

- `HashMap`：非线程安全，多线程 `put` 可能死循环（JDK7 头插法）或数据丢失。
- `Hashtable`：所有方法 `synchronized`，粒度粗、性能差，已过时。
- `ConcurrentHashMap`：
  - JDK 7：分段锁 `Segment`，锁粒度到段。
  - JDK 8：**数组 + 链表/红黑树**，用 `synchronized` 锁**桶头节点** + CAS，粒度更细，并发度更高；`size` 用 `baseCount + CounterCell`（类似 LongAdder）。

### 30. `ConcurrentHashMap` 为什么 key/value 不能为 null？

多线程下 `get` 返回 null 有歧义（是"没这个 key"还是"值就是 null"），无法用 `containsKey` 消除竞态，故禁止 null（`HashMap` 单线程无此问题）。

### 31. 常见阻塞队列有哪些？

- `ArrayBlockingQueue`：有界数组，一把锁。
- `LinkedBlockingQueue`：可选有界链表，读写两把锁（吞吐更高），默认无界需警惕 OOM。
- `SynchronousQueue`：无容量，一个 put 必须配一个 take（`newCachedThreadPool` 用它）。
- `PriorityBlockingQueue`：优先级无界队列。
- `DelayQueue`：延时队列（定时任务、缓存过期）。

## 九、死锁

### 32. 死锁产生的四个必要条件？

1. **互斥**：资源同一时刻只能被一个线程占有。
2. **持有并等待**：持有资源同时等待其他资源。
3. **不可剥夺**：资源只能由持有者主动释放。
4. **循环等待**：存在线程互相等待的环。

四个条件同时满足才会死锁，破坏任意一个即可避免。

### 33. 如何避免死锁？

- **破坏循环等待**：所有线程按**固定全局顺序**申请锁（最常用）。
- **破坏持有并等待**：一次性申请所有资源。
- **破坏不可剥夺**：用 `tryLock(timeout)`，拿不到就释放已持有的锁重试。
- 减少锁粒度、用并发容器、用无锁数据结构。

### 34. 怎么排查死锁？

- `jps` 找进程号 → `jstack <pid>` 查看线程栈，会直接打印 `Found one Java-level deadlock`。
- `jconsole` / `VisualVM` 图形化检测。
- 生产可结合 Arthas `thread -b` 一键查阻塞线程。

## 十、并发工具类

### 35. `CountDownLatch`、`CyclicBarrier`、`Semaphore` 的区别？

| 工具 | 作用 | 能否重用 |
| --- | --- | --- |
| `CountDownLatch` | 一个/多个线程等待另一组线程完成（`await` 等到 `count` 归零） | 不可重用 |
| `CyclicBarrier` | 一组线程互相等待，都到达屏障点后一起继续 | **可重用**（reset） |
| `Semaphore` | 控制同时访问资源的线程数量（限流/连接池） | 可重复 acquire/release |

- 记忆：CountDownLatch 是"**减法计数、一次性**"；CyclicBarrier 是"**加法凑齐、可循环**"；Semaphore 是"**令牌/许可**"。

### 36. `ThreadLocal` 是什么？会有什么坑？

- 每个线程持有一份变量副本，实现线程隔离（如 `SimpleDateFormat`、数据库连接、用户上下文）。
- 原理：`Thread` 内有 `ThreadLocalMap`，key 是 `ThreadLocal`（**弱引用**），value 是值（强引用）。
- **内存泄漏坑**：key 被回收后 value 仍被 `ThreadLocalMap` 强引用，尤其在**线程池**中线程长期存活。**用完必须 `remove()`**（放 finally）。
- 跨线程/线程池传递上下文用 `InheritableThreadLocal`（父子线程）或阿里 `TransmittableThreadLocal`（线程池）。

## 十一、拓展（新特性）

### 37. Java 21 虚拟线程（Virtual Threads）了解吗？

- JDK 21 正式发布（Project Loom）。虚拟线程是 **JVM 调度的轻量级线程**，成千上万个虚拟线程映射到少量平台线程（载体线程）。
- 遇到阻塞（IO）时自动"卸载"载体线程，极大提升**IO 密集型**高并发吞吐，写同步阻塞代码即可获得异步性能。
- 创建：`Thread.ofVirtual().start(...)` 或 `Executors.newVirtualThreadPerTaskExecutor()`。
- 注意：不适合 CPU 密集型；`synchronized` 中的阻塞可能 "pin" 住载体线程（建议用 `ReentrantLock`）。
